## Objective

Create the deployable AlphaHound 2.0 Azure-native application foundation.

This task establishes infrastructure/application structure only.

**Do not redesign or change AlphaHound trading logic in this task.**

---

## Background

AH1 currently relies on Windows Task Scheduler for periodic ingestion and convergence execution.

AH2 replaces production scheduling/orchestration with:

- Azure Functions
- Azure Service Bus
- PostgreSQL
- Azure Key Vault
- Application Insights

Future phases will add Durable Functions, Model Gateway, probability models, and venue executors.

AH1 must remain untouched and operational.

## Scope

Create or validate the AH2 application skeleton for:

### 1. Azure Functions

Provide a clean Python Azure Functions project structure supporting:

- timer-trigger function
- Service Bus queue trigger
- health/status endpoint where appropriate
- shared configuration
- shared logging
- shared correlation ID utilities
- shared Postgres access layer/interface

The initial business functions may remain stubs but the architecture must be deployable/testable.

### 2. Service Bus

Create abstractions/configuration for:

- publishing messages
- consuming messages
- correlation ID propagation
- message ID
- retry-safe processing
- dead-letter/error logging strategy

Create at minimum one end-to-end sample workflow:

```text
Timer Function
 -> publish AH2 test event
 -> Service Bus
 -> Queue Function
 -> write structured success log
```

Do not submit or simulate financial orders.

### 3. PostgreSQL

Create a shared AH2 database connectivity layer.

Requirements:

- connection information from configuration/secrets
- connection pooling appropriate to Azure Functions/Postgres
- explicit timeouts
- safe cleanup
- structured error logging

Do not modify AH1 production tables.

If a migration mechanism is needed, establish the framework only.

### 4. Key Vault / configuration

Support:

- local development settings
- Azure managed configuration
- Key Vault references / managed identity-compatible pattern

No secrets committed to Git.

### 5. Application Insights / logging

Implement structured logging standards including:

- correlation ID
- function name
- event/message ID
- duration where practical
- success/failure
- exception context without secret leakage

### 6. Idempotency foundation

Define a reusable idempotency interface/pattern.

This task does not need full trading-order idempotency, but future functions must have a standard mechanism available.

### 7. Tests

Provide tests for the new shared foundation including:

- configuration loading
- correlation ID propagation
- message serialization/deserialization
- idempotency utility/contract
- database layer behavior with mocks/test double
- timer-to-message workflow logic
- queue consumer logic

## Architecture constraints

1. Python remains the primary language.
2. PostgreSQL remains system of record.
3. Azure Functions orchestrate.
4. Service Bus handles asynchronous workflow messages.
5. All future model calls will go through a Model Gateway; do not hard-code model/provider dependencies into Functions.
6. Code must be testable outside Azure where practical.
7. Business logic must not be embedded directly inside trigger handlers.
8. Trigger handlers should delegate to services.
9. No secret values in source/config committed to Git.
10. All external operations require explicit timeout/error handling.
11. The foundation must support correlation IDs throughout the request/event chain.
